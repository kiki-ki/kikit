# 1 回のレビューのやり方

PR のレビューと自分の変更のレビューで共有する、1 回分のレビューの手順を示す。レビューの対象と目的、確かめた指摘をどう扱うかは、呼び出し元のスキルが決める。

## 1. /code-review を呼ぶ

`/code-review medium --max-findings default <対象>` を呼ぶ。level と `--max-findings` は、省くとユーザーが前回指定した値を引き継ぐので、必ず指定する。結果がバックグラウンドから届くときは、手順 2 を進めながら待つ。

## 2. 観点で確かめる

`/code-review` が見ないものを、次の観点で確かめる。バグ、再利用、単純化、効率は `/code-review` に、書式や静的に分かる誤りは linter に任せ、ここでは扱わない。

| 観点 | 見ること | 指摘の根拠になるもの |
|---|---|---|
| 目的 | 変更が目的を満たしているか | 目的のうち、diff のどこにも対応しないもの |
| スコープ | 目的と関係のない変更が混ざっていないか。PR なら本文と diff が食い違っていないか | 目的に結び付かない diff の箇所 |
| テスト | 変更した振る舞いを、実物を動かすテストが確かめているか。モックの呼び出しや実装の写しだけを確かめていないか。状態機械や並行処理のように組み合わせの多いロジックを変えたなら、例のテストだけで済ませていないか（[principle-prove-it-works](../../principle-prove-it-works/SKILL.md)）。CI が失敗していれば、原因が変更にあるか | テストが通ったままになる壊し方 |
| 根本原因 | nil チェック、例外の握りつぶし、リトライのような、症状を黙らせるガードで直していないか。同じパターンがほかに残っていないか。[principle-fix-root-causes](../../principle-fix-root-causes/SKILL.md) | 原因のある箇所、grep で見つかる同じパターン |
| 仕組みで守る制約 | コメントやドキュメントだけで守らせている制約のうち、型、テスト、lint で守れるものがないか。[principle-encode-lessons-in-structure](../../principle-encode-lessons-in-structure/SKILL.md) | 制約を守らせる型、テスト、lint の案 |
| 正の置き場 | 変更が値、定義、説明の写しを新しく作っていないか。写しのある情報を片方だけ直していないか。前からある写しは対象にしない。[principle-keep-one-source-of-truth](../../principle-keep-one-source-of-truth/SKILL.md) | 写し元と写しの箇所、直し残した写し |
| セキュリティ | secret の混入、信頼境界での入力の検証、権限の確認 | secret の行、検証されずに使われる入力、確認なしに通る操作 |

## 3. 指摘を分けて確かめる

`/code-review` と手順 2 の指摘のうち、同じものはまとめ、次の種類に分ける。種類と起こりやすさは、見積もれるだけのコードを読んで決める。起こりにくいものや、起きても影響の小さいものは、ここで捨てる。

| 種類 | 意味 |
|---|---|
| `must` | 完了やマージの前に直す必要がある |
| `want` | 直してほしいが、完了やマージは止めない |
| `nits` | 小さな改善 |
| `ask` | 意図や前提を確かめたい |

残った指摘は、変更後のコードや目的の説明の具体的な箇所を根拠として示せるかを確かめる。根拠は、バグなら壊れる入力や状態、スコープなら目的と diff の食い違い、再利用なら置き換え先のコードになる。意図がすでに説明されているものや、すでに解消済みのものは捨てる。

- `must` と `want` は、根拠が見つかるまで呼び出し元や関連するコードを読む。読んでも確かめきれなければ、捨てずに `ask` へ回す
- `nits` は、根拠をすぐに示せなければ捨てる
