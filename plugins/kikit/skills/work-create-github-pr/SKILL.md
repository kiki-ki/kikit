# work-create-github-pr

diff から読み取れないことだけを書いた PR を作る。

読み手は、いまのレビュアーと、あとで履歴を検索して変更の理由を知りたい人の両方になる。squash でマージすると本文はコミットメッセージにもなるので、リンク先が読めなくなっても分かるように書く。

## 手順

1. base を決める。指定がなければ、リポジトリの既定のブランチにする
2. `git log <base>..HEAD` と `git diff <base>...HEAD` で PR が含む変更を読む。関係のない変更や未コミットの変更があれば、止まってユーザーに確かめる
3. ブランチが push されていなければ `git push -u origin <branch>` で push する
4. [work-technical-writing](../work-technical-writing/SKILL.md) を読んでから、タイトルと本文を書く。`.github/pull_request_template.md` があれば、下のテンプレートの代わりにその節立てを使う
5. 下の「作る前に見直すこと」で見直す
6. `gh pr create --draft --base <base> --title "<タイトル>" --body "$(cat <<'EOF' ... EOF)"` で作る。シングルクォートの heredoc は本文をそのまま渡すので、backtick、`$`、`\` はエスケープしない
7. PR の URL をユーザーに伝える

## タイトル

`type(scope): summary` の形で書き、type は Conventional Commits のもの（`feat`、`fix`、`docs` など）にする。summary は、本文を開かずに何をする PR かが分かるように書く。英語なら命令形にする。

## 本文テンプレート

本文は、リポジトリの既存の PR と同じ言語で書く。英語なら、見出しを Intent、Approach、Impact、Testing にする。実装方針も影響もない小さな PR は、見出しを付けずに、意図と検証だけで書く。

各節を段落と箇条書きのどちらで書くかは、中身の量に合わせて [formats.md](../work-technical-writing/references/formats.md) で決める。検証だけは、チェックボックスの箇条書きで書く。

```markdown
Closes: <issue の完全な URL>

## 意図

この PR が何をし、なぜ要るかを簡潔に書く。経緯が長くなるなら、紐づく issue か設計のメモに書いてリンクする。

## 実装方針

どういう作りにしたかの要点を書く。別の案がありえた点だけ、選んだ理由を添える。

## 影響

利用者に見える変化、互換性のない変更、マージやデプロイの注意。

## 検証

- [x] 何をどう動かし、何が見えたかを、レビュアーが同じことをできる形で書く
```

`Closes:` の行は、紐づく issue があるときだけ書く。issue が複数なら、`- Closes: <URL>` の箇条書きで並べる。どちらの形でも、マージすると GitHub がその issue を閉じる。

影響の節は、書くことがあるときだけ置く。

確かめられることは、PR を作る前に確かめる。自分では確かめられず、人に任せたい確認があるときだけ、何をどう確かめてほしいかを検証の節に空のチェックボックスで書く。

レビュアーへの「特にここを見てほしい」という依頼は、本文ではなく PR のコメントで伝える。本文は squash でコミットメッセージになるので、レビューのためだけの案内を履歴に残さない。

## 作る前に見直すこと

- 本文が、いまの diff と食い違っていない
- diff を読めば分かること（ファイルや関数ごとの変更の列挙、コードの逐語的な説明）を書いていない
- 根拠のない「影響なし」と、セッション中のユーザーとのやり取りを書いていない
- ユーザーや team をメンションしていない。ハンドル名は、バッククォートで囲むか言い換えてある
- issue や PR を、`#123` ではなく完全な URL で参照している
