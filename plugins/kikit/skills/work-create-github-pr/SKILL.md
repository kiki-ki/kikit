# work-create-github-pr

レビュアーが diff と本文だけで、変更の意図を理解し、正しさを確かめられる PR を作る。本文には diff から読み取れないことだけを書く。

## 手順

1. ブランチの状態を確かめる
   - base: 指定がなければ、リポジトリの既定のブランチにする
   - 未コミットの変更があれば、PR に含めるかをユーザーに確かめる
   - `git log <base>..HEAD` と `git diff <base>...HEAD` で、PR に入るコミットと変更を読む。関係のない変更が混ざっていたら、止まって知らせる
2. ブランチが push されていなければ `git push -u origin <branch>` で push する
3. `.github/pull_request_template.md` があれば、下のテンプレートの代わりにその節立てに従う
4. [work-technical-writing](../work-technical-writing/SKILL.md) を読んでから、タイトルと本文を書く
5. `gh pr create --draft --base <base> --title "<タイトル>" --body "$(cat <<'EOF' ... EOF)"` で draft として作る。heredoc をシングルクォートで囲むと本文がそのまま渡るので、backtick、`$`、`\` はエスケープしない
6. 返ってきた PR の URL をユーザーに伝える

## タイトルと言語

- タイトルは `type(scope): summary` の形で簡潔に書く。type は Conventional Commits のもの（`feat`、`fix`、`docs` など）にする
- タイトルと本文は、リポジトリの既存の PR と同じ言語で書く。英語なら、テンプレートの見出しも英語にする

## 本文に書くこと

レビュアーが変更を理解して確かめるのに要ることだけを、要る量だけ書く。

- 変更の理由と、diff だけでは分からない変更の要点
- 設計判断と、検討して捨てた案とその理由
- 確かめたことと、その結果。何をどう動かしたかを、レビュアーが再現できる形で書く
- 確かめていないこと。推定は推定だと分かる形で書く
- マージの方法（squash してほしいなど）やコミットの順番に意味があれば、それも書く

次のものは書かない。

- ファイルや関数ごとの変更の列挙、コードの逐語的な説明
- 根拠のない「影響なし」
- 絵文字や太字などの装飾
- セッション中のユーザーとの細かいやり取り

GitHub に書き込む文の決まりも守る。

- ユーザーや team をメンションしない（`@username` や `@org/team` を書かない）。ハンドル名を書く必要があれば、バッククォートで囲むか言い換える
- 他の issue や PR は `#123` と書かず、`https://github.com/<owner>/<repo>/issues/123` のような完全な URL で参照する

## 本文テンプレート

既定では次の節で書く。中身のない節は省き、PR に合わせて節を足す（コミットの順番など）。

```markdown
## 何を変えたか

変更の要点と理由を書く。diff を読めば分かるファイルごとの変更は書かない。

## 設計の理由

採った方法を選んだ理由と、捨てた案を書く。迷う余地のない変更なら、この節ごと省く。

## 確かめたこと

- 実行したコマンドや操作と、その結果を並べる

## 未確認

- 確かめていないことと、確かめなかった理由を並べる
```
