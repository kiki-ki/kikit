# work-create-github-pr

diff から読み取れないことだけを書いた PR を作る。読み手は、いまのレビュアーと、あとで履歴を検索して変更の理由を知りたい人の両方になる。squash でマージすると本文はコミットメッセージにもなるので、リンク先が読めなくなっても分かるように書く。

## 手順

1. base を決める。指定がなければ、リポジトリの既定のブランチにする。`git log <base>..HEAD` と `git diff <base>...HEAD` で PR が含む変更を読む。関係のない変更や未コミットの変更があれば、止まってユーザーに確かめる
2. ブランチが push されていなければ `git push -u origin <branch>` で push する
3. [work-technical-writing](../work-technical-writing/SKILL.md) を読んでから、タイトルと本文を書く。`.github/pull_request_template.md` があれば、下のテンプレートの代わりにその節立てを使う
4. 下のチェックリストで見直す
5. `gh pr create --draft --base <base> --title "<タイトル>" --body "$(cat <<'EOF' ... EOF)"` で作る。シングルクォートの heredoc は本文をそのまま渡すので、backtick、`$`、`\` はエスケープしない
6. PR の URL をユーザーに伝える

## タイトル

`type(scope): summary` の形で書き、type は Conventional Commits のもの（`feat`、`fix`、`docs` など）にする。summary は、本文を開かずに何をする PR かが分かるように書く。英語なら命令形にする。

## 本文テンプレート

見出しはリポジトリの言語によらず次の英語にし、本文はリポジトリの既存の PR と同じ言語で書く。中身のない節は省き、PR に合わせて節を足す。理由が 1〜2 文で済む小さな PR は、見出しを付けずに段落だけで書く。

```markdown
## What

何が変わるかを 1〜3 行で書く。

## Why

なぜこの変更が要るか。紐づく issue があれば `Closes <issue の URL>` を書く。

## How

その方法を選んだ理由。捨てた案と、この方法の欠点も書く。

## Impact

利用者に見える変化、互換性のない変更、マージやデプロイの注意。

## Testing

- [x] 確かめたこと。何をどう動かし、何が見えたかを、レビュアーが同じことをできる形で書く
- [ ] 確かめていないこと。確かめなかった理由を添える
```

## チェックリスト

作る前に、本文とタイトルを次の項目で見直す。このチェックリストは本文に入れない。

- [ ] タイトルだけで何をする PR か分かる。「fix: バグを直す」のような要約になっていない
- [ ] リンク先を読まなくても、目的が本文だけで分かる
- [ ] 本文が、いまの diff と食い違っていない
- [ ] Testing の各項目に、何をどう動かし何が見えたかが書いてある。確かめていないことは空のチェックボックスで残してある
- [ ] diff を読めば分かること（ファイルや関数ごとの変更の列挙、コードの逐語的な説明）を書いていない
- [ ] 根拠のない「影響なし」、絵文字や太字の装飾、セッション中のユーザーとのやり取りを書いていない
- [ ] ユーザーや team をメンションしていない。ハンドル名は、バッククォートで囲むか言い換えてある
- [ ] issue や PR を、`#123` ではなく完全な URL で参照している
