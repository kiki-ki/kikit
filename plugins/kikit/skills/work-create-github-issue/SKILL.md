# work-create-github-issue

起票者の頭の中にしかない文脈を、着手する人に引き渡す issue を書く。着手する人が本文だけを読んで作業を始められ、close してよいかも判断できる状態にする。

## 手順

1. 起票したい内容をユーザーから受け取る。必要なら関連するコードや PR を調べて整理する
2. 起票先のリポジトリとラベルを決める。会話から明らかなら、決めた内容を示すだけでよい
   - リポジトリ: 指定がなければ、作業ディレクトリのリポジトリを候補として示す
   - ラベル: 付けるものがあるかを確かめる。付けるときは、`gh label list --repo <owner>/<repo>` で存在を確かめてから付ける
3. [work-technical-writing](../work-technical-writing/SKILL.md) を読んでから、下のテンプレートに沿って本文の下書きを作る
4. 下書きをユーザーに見せ、合意を取る。起票すると外部に公開されるので、合意なしに起票しない
5. `gh issue create --repo <owner>/<repo> --title "<タイトル>" --body "<本文>"` で起票する。ラベルを付けるときだけ `--label <ラベル>` を足す
6. 返ってきた issue の URL をユーザーに伝える

## タイトルと言語

- タイトルは `scope: summary` の形にする。scope には対象のサービスやコンポーネントの名前を入れる
- タイトルと本文は、起票先のリポジトリの既存の issue と同じ言語で書く。英語なら、テンプレートの見出しも英語にする

## 本文テンプレート

既定では次の節で書く。issue の種類に合わせて節を足したり省いたりする。

```markdown
## 概要

着手する人が内容をつかめる 1〜3 行の要約。作業の一覧は書かない。

## 背景・目的

なぜ必要か。着手する人が判断に迷ったときに立ち返る材料にする。経緯はすべて書かず、経緯が分かるリンクを貼る。

## ゴール

- close してよい条件を、確かめられる箇条書きで書く。作業の一覧や「改善する」のような願望は書かない
- 調査の issue なら、何が分かれば、または何が決まれば完了かと、結果をどこに書くか（issue のコメント、ドキュメントなど）を書く

## 作業内容

- [ ] ゴールに届くまでの作業を、分かっている範囲で並べる。ゴールを言い換えただけの項目にしない
- [ ] 着手した後に書き換えてよい。起票の時点で決まっていなければ、この節ごと省く

## 参考情報

- 関連するファイル、似た PR、ドキュメント。それぞれ何の参考になるかを添える
```

- スコープが広がりそうなら、ゴールに「やらないこと」を足す
- ゴールが互いに独立した複数の話になったら、issue を分ける
