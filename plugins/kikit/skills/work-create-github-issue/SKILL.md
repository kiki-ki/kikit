# work-create-github-issue

起票者の頭の中にしかない文脈を、着手する人に引き渡す issue を書く。着手する人が本文だけを読んで作業を始められ、close してよいかも判断できる状態にする。

## 手順

1. 起票したい内容をユーザーから受け取る。必要なら関連するコードや PR を調べて整理する
2. 起票先のリポジトリとラベルを決める。会話から明らかなら、決めた内容を示すだけでよい
   - リポジトリ: 指定がなければ、作業ディレクトリのリポジトリを候補として示す
   - ラベル: 付けるものがあるかを確かめる。付けるときは、`gh label list --repo <owner>/<repo>` で存在を確かめてから付ける
3. `gh issue list --repo <owner>/<repo> --state all --search "<キーワード>"` で、同じ課題の issue がないかを探す。close 済みの issue も対象にする。見つかったら、新しく起票するか、既存の issue へのコメントで済ませるかをユーザーに決めてもらう
4. [work-technical-writing](../work-technical-writing/SKILL.md) を読んでから、下のテンプレートに沿って本文の下書きを作る
5. 下の「起票する前に見直すこと」で見直す
6. 下書きをユーザーに見せ、合意を取る。起票すると外部に公開されるので、合意なしに起票しない
7. `gh issue create --repo <owner>/<repo> --title "<タイトル>" --body "$(cat <<'EOF' ... EOF)"` で起票する。シングルクォートの heredoc は本文をそのまま渡すので、backtick、`$`、`\` はエスケープしない。ラベルを付けるときだけ `--label <ラベル>` を足す
8. 返ってきた issue の URL をユーザーに伝える

## タイトルと言語

- タイトルは `scope: summary` の形にする。scope には対象のサービスやコンポーネントの名前を入れる
- タイトルと本文は、起票先のリポジトリの既存の issue と同じ言語で書く。英語なら、見出しを Summary、Background、Done criteria、Approach、References にする

## 本文テンプレート

既定では次の節で書く。方針と参考は、書くことがなければ節ごと省く。

各節の書き方は、中身に合わせて [formats.md](../work-technical-writing/references/formats.md) で選ぶ。完了条件だけは、チェックボックスの箇条書きで書く。

```markdown
## 概要

何を、なぜ変えるかを 1〜2 行で書く。作業の一覧や、背景の繰り返しは書かない。

## 背景・目的

- 今どうなっているかを、事実と根拠のリンクで書く。バグなら、再現手順、期待する動作、実際の動作を書く
- なぜ変えるのかを書く。着手する人が判断に迷ったときに立ち返る基準になる。経緯はすべて書かず、経緯が分かるリンクを貼る

## 完了条件

- [ ] close してよい条件を、確かめられる形で書く。作業の一覧や「改善する」のような願望は書かない

## 方針

- 進め方の案と、その理由を書く。決まっていないことがあれば、決める手がかりを添える

## 参考

- 関連するファイル、似た PR、ドキュメント。それぞれ何の参考になるかを添える
```

- 調査の issue なら、何が分かれば完了か、または何が決まれば完了かを完了条件に書く。結果を書く先も添える。書く先は、issue のコメントやドキュメントなどになる
- スコープが広がりそうなら、完了条件のチェックリストの後に、やらないことを書く
- 完了条件が互いに独立した複数の話になったら、issue を分ける
- 方針に書く案のうち、確かめていないものは推測だと分かるように書く

## 起票する前に見直すこと

- ユーザーや team をメンションしていない。ハンドル名は、バッククォートで囲むか言い換えてある
- issue や PR を、`#123` ではなく完全な URL で参照している
- 公開のリポジトリなら、社内のシステムの URL や、外に出せない情報を書いていない
