# principle-prove-it-works

作業の結果は本物を直接見て確かめる。間接的な手がかり（ファイルの更新時刻、出力が新しいこと、エージェントの自己申告、キャッシュされたスクリーンショット）から推測しない。間接的な確認は安く見えるが、間違った推測のまま進めたときのコストのほうがずっと大きい。

- プロセスが動いているかは、派生した状態からではなく直接確かめる
- キャッシュや派生した表現ではなく、実際の値を読む
- 確認が失敗したら、システムを疑う前に確認の方法を疑う

確かめた結果（実行したコマンドと出力、読んだ値、diff）をユーザーに見える形で示してから、完了と言う。自明でない確認は再実行できるスクリプトにする（[principle-build-the-lever](../principle-build-the-lever/SKILL.md)）。

## 組み合わせが多いものを確かめるとき

状態機械、並行処理、パーサー、シリアライズの往復のように、入力や状態の組み合わせが多いものは、例をいくつか試しても確かめたことにならない。試していない組み合わせで壊れるからだ。この節は、組み合わせを決めるロジックそのものを変えたときに適用する。その周りの表示や名前を変えただけなら、ふだんの確かめ方でよい。

満たすべき性質（不変条件）を書き出し、組み合わせ全体に対して確かめる。方法は安い順に次のとおりで、足りる最初のものを選ぶ。

1. ありえない状態を型で表せないようにする
2. property-based testing で、生成した多数の入力に対して性質を確かめる
3. 状態の数が小さければ、すべてを列挙して性質を確かめるスクリプトを書く
4. 形式的検証をする。並行や分散のプロトコルのように、テストで再現しにくく、壊れたときの損失が大きい設計は、TLA+ などのモデル検査で反例を探す

方法は、プロジェクトにすでにある型やテストの仕組みから選ぶ。新しいライブラリやモデル検査の道具を持ち込むときは、先にユーザーへ提案して合意を取る。
