# work-handle-out-of-scope-findings

スコープ外の発見は、大きさで扱いを分ける。どれも取りこぼさず、タスクの最後に報告する。全部を今の変更に混ぜるとレビューしにくくなり、全部を後回しにすると気づいた文脈ごと失われる。

## 1. スコープ内かを決める

今のタスクを止めるものは、スコープ内として扱う。それを直さないと、今のタスクを完了できないか、完了を確かめられないものだ。本筋の変更とは別のコミットにして、先に直す。

## 2. 扱いを決める

それ以外の発見は、次のどれかで扱う。迷ったら、後ろに書いた扱いを選ぶ。

- 混ぜる: 本筋で触っているファイルの中にあり、数行で直せて、レビュアーが理由を聞かずに分かるもの。typo、古いコメント、本筋が使う関数の誤った説明などが当たる。本筋とは別のコミットにする。本筋で書き換えている行の中なら、同じコミットでよい
- 任せる: 直し方がはっきりしていて、本筋とは別のファイルや論点になるもの。下の「3. サブエージェントに任せる」に従う
- issue にする: 直し方が決まっていないもの、設計や仕様の判断が要るもの、影響が広いもの。場所、問題、根拠を記録して本筋に戻り、タスクの最後に [work-create-github-issue](../work-create-github-issue/SKILL.md) に従って起票する

記録はタスクリストなど、セッションの終わりで見返せる場所に置く。memory には置かない。根拠が確かめていない推測なら、推測と書く。

## 3. サブエージェントに任せる

Agent ツールで、`isolation` に `worktree` を指定したサブエージェントを起動する。今の作業ツリーとぶつからないように、別のワークツリーと別のブランチで直させるためだ。渡すものは次のとおり。

- 問題と、その根拠
- 直し方と、触ってよい範囲
- 確かめ方
- コミットまででとどめ、push と PR の作成はしないこと

本筋は、サブエージェントを待たずに進める。終わったら、サブエージェントの報告をうのみにせず、diff と確かめた結果を読む。ユーザーが別のセッションで進めたいと言ったら、同じ内容を依頼文にして渡す。

## 4. 報告する

タスクの報告の後に、扱いごとに一覧を出す。

- 混ぜたもの: コミット
- 任せたもの: ブランチ、diff の要点、確かめた結果
- issue にするもの: 起票した issue の URL か、起票前の下書き

push、PR の作成、issue の起票のように外に書き込む操作は、ユーザーの合意を取ってから行う。
