# work-review-own-changes

自分の変更を別のレビュアーに見せ、確かめた指摘だけを直して、再びレビューさせる。これを、直すべき指摘がなくなるまで繰り返す。1 回のレビューは、PR のレビューと同じ [review-round.md](../work-review-github-pr/references/review-round.md) の手順で行う。

## 範囲と目的

ベースブランチ（既定は `main`）に対する、作業ツリーを含む diff を対象にする。新しく作ったファイルは `git diff` に出ないので、`git status --short` で拾う。

始める前に、変更の目的をユーザーの依頼から 1 文で書く。言えなければユーザーに聞く。目的は、指摘がスコープの内か外かを分ける基準になる。

## 回数の上限

1 ラウンドで、`/code-review` を 1 回と、サブエージェントを 1 体実行する。費用はラウンドの数に比例するので、上限を決めてから始める（[principle-guard-the-context-window](../principle-guard-the-context-window/SKILL.md)）。

上限は既定で 3 ラウンドとし、始めるときにユーザーへ示す。上限を上げるときは、ユーザーの合意を取る。

## 1 ラウンドの手順

### 1. 指摘を集めて確かめる

review-round.md の手順に従う。ただし、次の点は自分の変更に合わせて変える。

- `/code-review` は、対象を付けずに呼ぶ。手元の diff が対象になる
- 観点での確認は自分でせず、Agent ツールで起動した general-purpose に任せ、`/code-review` と並列に実行する。書いた本人は文脈を知っているので、自分の変更の問題に気づきにくいからだ。review-round.md の「2. 観点で確かめる」の節を言い換えずに渡し、目的と範囲も渡す。判定役にはファイルを編集させず、指摘ごとに `file:line`、観点、根拠を返させる
- `ask` と `nits` は直さずに、最後の報告に載せる
- 今の変更が原因でない指摘は、スコープの外の発見として [work-handle-out-of-scope-findings](../work-handle-out-of-scope-findings/SKILL.md) に従って扱う

### 2. 直して確かめる

確かめた `must` と `want` を、症状ではなく原因のところで直す（[principle-fix-root-causes](../principle-fix-root-causes/SKILL.md)）。直したら、プロジェクトのテスト、ビルド、lint のうち変更に関わるものを実行し、通ることを確かめる。通らなければ、次のラウンドより前に直す。

直した変更はコミットせず、作業ツリーへ残す。コミットの分け方は、呼び出し元の作業の進め方に従う。

### 3. 続けるかを決める

次のどれかに当たったら止める。どれにも当たらなければ、diff 全体を範囲にして次のラウンドに進む。直した箇所がほかの箇所を壊すことがあるので、範囲は直した箇所に絞らない。

- 確かめた `must` と `want` が 0 件だった。収束したとみなす
- 上限のラウンドに達した。残った指摘は未解決として報告する
- 前のラウンドで直した箇所を元に戻す指摘か、直したはずの指摘が、また出た。どちらの直し方を採るかをユーザーに決めてもらう

前のラウンドで捨てた指摘がまた出たときは、同じ理由で捨てる。止める理由にはしない。

## 報告

ラウンドごとに、次のものを報告する。

- 指摘の件数
- 直した指摘と、その確認に実行したコマンドと結果
- 捨てた指摘と、その理由

最後に、止めた理由と、残ったものを報告する。残ったものは、未解決の `must` と `want`、`ask`、`nits`、スコープの外の指摘とその扱いに分ける。
